# Data Transformation Pipeline

## Power boundaries

`lib/power/power-basis.ts` derives the three boundaries beyond GPU-measured telemetry as J per successful output token and J per total (input + output) token, plus W per allocated GPU for B4; `POWER_BASIS_FIELDS` maps every basis × quantity, B1 included, to its `InferenceData` field. B2 and B3 watts are one rating per hardware, so they are not chart fields; the power timelines (`PowerTimeline`, the per-run `GpuPowerChart`) draw them as reference lines. `buildDerivedChartFields` writes the power-basis fields (`writePowerBasisChartFields`) right after the measured fields, so the official chart, the `?unofficialrun=` overlay (`transformBenchmarkRows`), and Historical Trends (`rowToLightweightPoint` with `requestedMetrics`) share one formula set; each key is gated by `wants(key)` so selective output stays exact. With `requestedMetrics`, the measured and power-basis groups are not built at all unless a requested key belongs to them (`MEASURED_POWER_FIELD_KEYS`, `POWER_BASIS_FIELD_KEYS`); both builders are pure, so the output is the same.

| Basis                                    | W / GPU                                                                    | J / output token                   | J / total token                 | Fields                                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------- |
| B1 GPU measured                          | `avg_power_w`                                                              | `joules_per_output_token`          | `joules_per_total_token`        | existing `measuredAvgPower`, `measuredJPerOutputToken`, `measuredJPerTotalToken` (unchanged) |
| B2 GPU provisioned                       | `HW_REGISTRY.tdp`                                                          | `W × N_alloc ÷ total output tok/s` | `W ÷ tput_per_gpu`              | `gpuProvisionedJPerOutputToken`, `gpuProvisionedJPerTotalToken`                              |
| B3 utility provisioned (all-in)          | `HW_REGISTRY.power × 1000`                                                 | `W × N_alloc ÷ total output tok/s` | `W ÷ tput_per_gpu`              | `utilityProvisionedJPerOutputToken`, `utilityProvisionedJPerTotalToken`                      |
| B4-IT IT modeled (measured → IT, no PUE) | `modeledSystemPower.deploymentItWatts ÷ modeledSystemPower.gpuCount`       | `B1 J/out × (B4-IT W ÷ B1 W)`      | `B1 J/total × (B4-IT W ÷ B1 W)` | `itModeledWatts`, `itModeledJPerOutputToken`, `itModeledJPerTotalToken`                      |
| B4 utility modeled (measured → IT → PUE) | `modeledSystemPower.deploymentFacilityWatts ÷ modeledSystemPower.gpuCount` | `B1 J/out × (B4 W ÷ B1 W)`         | `B1 J/total × (B4 W ÷ B1 W)`    | `utilityModeledWatts`, `utilityModeledJPerOutputToken`, `utilityModeledJPerTotalToken`       |

- **N_alloc and total throughput** (`powerBasisNormalization`). Aggregate rows report output per allocated GPU, so `N_alloc` cancels and the builder uses `W ÷ output_tput_per_gpu` without trusting display counts (legacy ingest can encode TP × EP twice). Disaggregated rows report output per decode GPU while the deployment also powers the prefill pool, so `total output tok/s = output_tput_per_gpu × num_decode_gpu` and `N_alloc = num_prefill_gpu + num_decode_gpu`; the article's 4P+4D counts eight GPUs, and B3 energy is `(P + D) / D` times `jOutput` on such rows. This holds for AgentX rows too: the AgentX producer divides by every GPU, so ingest, the `db:backfill-agentic-disagg-throughput` backfill, and the benchmark queries move those rows to the per-pool basis and keep the producer's rates as `input_tput_per_total_gpu` / `output_tput_per_total_gpu`. When the chip-basis toggle is on `total` (`chip_basis: 'total'`), output is per deployment GPU, so the multiplier becomes `num_prefill_gpu + num_decode_gpu` and every boundary is identical on both bases. Legacy Dynamo rows (2025-09-29 to 2025-12-05) are marked disaggregated but record no workers and store the whole deployment N in both pool fields, so `N_alloc = N` (and `physicalChips = N`). Some carry input and output per deployment chip (most of October 2025) and are used as stored; later ones are per pool with unrecorded pool sizes, and the prefill share p solves `tput_per_gpu = input × p + output × (1 − p)` exactly, giving total output tok/s `output × (1 − p) × N` and the total-basis rates. ISL:OSL is a fallback only when input equals output. Rows missing either rate are used as stored. The producer divides total (input + output) throughput by every allocated GPU for aggregate and disaggregated rows alike, so J per total token is `W ÷ tput_per_gpu` with `N_alloc` cancelled; it keeps the output normalization's availability gate, so a boundary publishes J per total token exactly where it publishes J per output token. B3 J per total token therefore equals the ungated `jTotal` wherever both exist.
- **B3 meter.** `HW_REGISTRY.power` is all-in utility power per GPU (host, networking and cooling, PUE included), so B3 applies no further PUE and sits at the same meter as B4.
- **B4 source.** Reuses the `SystemPowerEstimate` that `rowToAggDataEntry` attached as `entry.modeledSystemPower`; nothing re-runs `modelSystemPower`. `deploymentFacilityWatts` is modeled IT power (chassis or rack AC plus its scale-out network share) × PUE with PUE applied exactly once inside `estimateChassisPower` or `estimateRackPower`, divided by the physical measured GPU count (not `modeledGpuCount`, which over-counts partially allocated chassis: a 4P+4D deployment on two worker hosts models 16 GPUs while measuring 8, and the unit test pins that divisor). Modeled energy scales the producer's same-window `joules_per_output_token` and `joules_per_total_token` by `B4 W ÷ avg_power_w`, so it inherits B1's token denominators and survives rows whose `output_tput_per_gpu` is missing (the provisioned energies do not; a per-basis point count cannot assume one shared denominator).
- **Null rules.** A value is emitted only when finite and positive; otherwise the key is omitted (never `{ y: 0 }`), because the metric filters drop points by `metricKey in point` and `remapInferencePoint` falls back to raw throughput when a key exists with an unusable value. B2/B3 energies are absent for hardware without registry specs (`getGpuSpecs` returns zeros), without output throughput, or without disaggregated counts. B4 requires `modeledSystemPower.status === 'supported'` and B1 watts (`avg_power_w` after `rowToAggDataEntry`'s `power_valid !== 0` admission); B4 energy additionally needs `joules_per_output_token` (J/out) or `joules_per_total_token` (J/total). Telemetry admission belongs to `modelSystemPower`, which accepts `power_valid === 1` with schema v2 or the validated unversioned single-node producer (`telemetryBasis: 'validated-unversioned-single-node'`), so B4 shares B1's telemetry admission; benchmark types without an upstream workload state (`reason: 'workload'`), unsupported hardware (`reason: 'hardware'`), and telemetry/topology failures withhold it. GB200/GB300 NVL72 rows take an equal compute-tray share of `estimateRackPower`, the pinned `power_model` rack evaluated at the measured W/GPU and, when the row carries complete, matching Grace-socket telemetry from the same window, the measured W per Grace socket; otherwise the rack's modeled Grace profile (`unit: 'nvl72-tray'`, `cpuBasis: 'measured' | 'modeled'`). The public API's `strictV2` row filter is not re-applied in the chart for B1, so it is not re-applied for B4 either.
- **Ordering invariant** (unit-tested on real B200 telemetry): B3 ≥ B4 ≥ B1 and B2 ≥ B1 for both W/GPU and J/out on the same point.
- **Token-mix invariant** (`power-basis.test.ts`, aggregate and 8P + 8D disaggregated rows): every boundary's J/out ÷ J/total equals B1's, the served total-to-output token ratio.
- **Reconstructed prefill energy** (`reconstructedPrefillJPerOutputToken`, `utils/role-energy.ts`). For validated (`power_valid === 1`, schema 2) disaggregated rows, `prefill_joules_per_input_token × (joules_per_output_token ÷ joules_per_input_token)` carries the prefill pool's energy onto the output-token axis: the ratio is the served input:output token count because schema-2 aggregate energy has one numerator. With `decode_joules_per_output_token` it sums back to the deployment's J/out. It feeds only the `i_pcompare=roles` comparison on the energy axis (PowerX Figure 7) and is never a y-axis of its own; aggregate rows and rows missing any of the four inputs omit it.
- Historical Trends substitutes `output_tput_per_gpu := tput_per_gpu` for legacy rows lacking output throughput; provisioned energies in trends inherit that fallback.

## Prefix-Cache Tier Shares (`/cache-reuse`)

The Prefix Cache Reuse tab stacks, per concurrency, where one configuration's prompt tokens came from: the chip's HBM KV cache, the host tier behind it, or nowhere (recomputed). It reads the calculator's `GPUDataPoint` groups (`useThroughputData`) and takes the tiers from each point's `sourceRow.metrics`, so official rows and `?unofficialrun=` overlays flow through the same mapper; the pure logic lives in `components/calculator/cache-reuse.ts`.

Why the shares are built the way they are:

- **The host segment is the CPU-offload rate**, falling back to `server_external_cache_hit_rate` only when a row reports no CPU figure, and the two are never summed. This deliberately differs from `measuredCacheHitRate` in `lib/calculator/cache-pricing.ts`, which prefers the external figure to price cached input conservatively: that protects a revenue number from double-counting, while this chart names the tier a token came from, and on SGLang HiCache rows the host tier is the CPU figure (it is also what the GLM-5.3 article plotted).
- **TensorRT-LLM with offload reports one combined figure.** The point summary already labels it "Combined chip + CPU"; the tab draws it as a single reused segment (`combined: true`) instead of inventing a split.
- **Clamping is visible, not silent.** Some rows report a GPU rate above 1 (GB300 Dynamo, 1.012). Shares are clamped so the bar sums to 100%, and the unclamped `reportedTotal` is kept for the tooltip caveat.
- **Rows without any tier are drawn as gaps, not zeros.** A GB300 sweep scraped only at the Dynamo frontend has a theoretical ceiling but no server counters; those concurrencies get a marker and remain in the API’s `unmeasured` list.
- **Fixed sequences record no cache tier at all**, so the tab keeps the scenario selector and shows an explanatory empty state rather than an empty chart.

The configuration selector defaults to the group with the most tiered rows, preferring SGLang on a tie because SGLang separates the two tiers. Overlay runs on the same hardware become their own outlined series so a branch can be read against the published curve concurrency by concurrency; no series mixes recipes.

The tab is footer-only, so the agentic chart links into it. `cacheReuseHref` (`lib/calculator/cache-reuse-link.ts`) writes the point's own `g_model`, `g_rundate`, `i_seq`, `i_prec`, `c_cfg`, and `c_recipe` (clearing an inherited `g_runid`) because a reader who landed cold has no in-memory chart state to inherit; pinning one precision matters because with several selected the groups are keyed `hwKey__precision` and a bare hardware key would miss.

## Chart Point Construction

`createChartDataPoint` copies the entry into one literal and then writes the derived metric fields into that same object in their fixed order. Spreading a separately built derived-field object made V8 copy about 40 keys per point through its slow runtime path. `transformBenchmarkRows` builds each row's point once for the first chart definition and clones it with the other chart's `x` and `y`, since both charts share the row's derived fields. It builds them as each row is converted and groups the points, not the entries, by hardware key, so an `AggDataEntry` dies with its row instead of living until the whole batch is grouped. The hardware config reads the model and run URLs from the points. Holding every entry for the whole pass had kept about 110 MB more peak RSS over 50 repeated transforms.

The derived-field writers (`writeThroughputChartFields`, `writeMeasuredPowerChartFields`, `writePowerBasisChartFields`) take the requested metrics as a lookup built once per pass (`derivedMetricRequest`), or `undefined` for every metric. They test a key per metric instead of calling a predicate per metric, which had been 22 calls for each trend point. `writePowerBasisChartFields` computes and writes each boundary directly, with no intermediate value object, and `powerBasisNormalization` reads a split disaggregated row's pool sizes once.

`buildInferenceSeries` (the `/api/v1/views/inference` route) needs one chart and the selected precisions only. `transformChartRowsForPrecisions` builds just those points but still opens each hardware group at its first row of any precision, so point order matches `transformBenchmarkRows` followed by a precision filter.

Historical Trends prepares each row once per load (`prepareTrendRows`). That pass stores the metric-independent part of the trend point, the throughput inputs (with the legacy `output_tput_per_gpu := tput_per_gpu` fallback applied) and the row's supplemental token-metric support. A metric change then clones the prepared point and writes only the requested derived fields into the clone (`writeThroughputChartFields`), with no intermediate field object to spread. The full `rowToAggDataEntry` entry is built, once per row, only when a requested metric reads measured power or a power boundary (`requestsPowerChartFields`), and those fields go through `writeDerivedChartFields` the same way.

Every object a trend pass builds (grouped points and their metric values, buckets, line points) lives until the pass ends. V8 tracks object and array literals per allocation site, and when a scavenge lands inside the first, unoptimized pass and finds a site's objects still alive, it allocates that site's objects straight into the old generation from then on. Each later pass then leaves its garbage there until the next mark-compact, so repeated metric changes peaked at 429 MB of RSS against 254 MB for the same work. Class instances, object spreads, array spreads and array builtins (`map`, `filter`) carry no allocation site. The trend pipeline therefore builds its long-lived per-row and per-bucket objects that way. `chartMetric` spreads a template, `TrendBucket` and `MeasuredTrendPoint` are classes, and grouping, source and line arrays are spread from a shared empty array (`[...NO_POINTS]`) or come from `map`. `Array.of` has no allocation site either, but it is a generic builtin call. Creating and filling a small array with it took about 78 ns in the lab against about 40 ns for the spread and 34 ns for a literal, and a metric change creates two arrays per bucket. A bucket keeps only its curve's `at`, so the curve literal itself dies at once. Literal arrays that hold such objects only for one call are exposed too. When `evaluateTrendCurves` collected `[start, groupKey, points]` tuple literals, about half of the slider runs promoted every line point at each scavenge and took 50% longer. It now keeps the points in a `Map` and orders the group keys with plain arrays of strings and numbers. A plain literal in that path brings the regression back. `lab/` RSS and wall runs catch it, unit tests cannot.

A slider move (`evaluateTrendCurves`) evaluates each group's buckets in one pass and orders the lines by the date-major position of each group's first bucket with a value, so it no longer builds a value array over every bucket or looks up the line map once per bucket. Line points share their bucket's provenance array (`TrendDataPoint.sources` is `readonly`) instead of copying it on every move.

## Hardware Key Construction

This is the most complex and bug-prone part of the pipeline. A bad hardware key produces either a missing legend entry, zeroed cost/energy metrics (because `getGpuSpecs` returns zeros), or a chart point that never matches the active hardware filter.

**GPU specs lookup** happens once per hardware key in `transformBenchmarkRows` and `transformChartRowsForPrecisions`, which pass the specs to `createChartDataPoint`; other callers let `createChartDataPoint` or `buildDerivedChartFields` look them up. `getGpuSpecs(hwKey)` (`lib/catalog/constants.ts`) splits on `[-_]` to extract the base GPU token (for example, `"b200_trt_mtp"` becomes `"b200"`) and looks it up in `HW_REGISTRY`. Missing keys return zeroed specs, producing `0` cost/energy values rather than crashing.

**User-entered GPU costs** (`calculateCostsForGpus`, `lib/shared/utils.ts`) are keyed by `hwKey.split('_')[0]`, so every framework and spec-decoding variant of a GPU (`b200_trt`, `b200_trt_mtp`) inherits its base GPU's cost.

Agentic keys deliberately omit the spec-decoding suffix because one production curve may combine speculative and standard-decoding points; `spec_decoding` remains on each point for filtering, tooltip metadata, and point-level identity.

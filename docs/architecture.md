# Architecture Decisions

See [App Source Organization](./source-organization.md) for component/provider
ownership and conventions for preserving module boundaries.

## Client-First, API-Passthrough

Raw-data API routes return raw DB rows with zero transformation, validation, or filtering. All presentation logic lives in the frontend. This isn't laziness — it's intentional:

- **Caching**: Raw responses are maximally cacheable (1-day CDN cache). Any server-side filtering would multiply cache keys and reduce hit rates.
- **Flexibility**: The frontend changes far more often than the data shape. Keeping transformation client-side means API routes never need updating for new chart metrics, filter logic, or display formats.
- **Simplicity**: No DTOs, no mappers, no validation gatekeeping. The DB schema IS the API contract.

### Deliberate API Exceptions

Some routes serve a purpose that raw DB rows cannot satisfy:

- Dashboard projections under `/api/v1/views/*` use shared pure UI transformations server-side and publish their selectors and assumptions. Keep raw-data contracts separate from these projections.
- CollectiveX assembles its stored committed-result documents through its shared reader.
- OperatorX uses versioned ingest-time comparison projections for its page-owned API. The reader merges compact timing rows across runs while preserving source revisions, statuses, and timeline references; raw documents remain available for drilldowns. An optional revision-keyed Blob cache shares the merged comparison across instances; partial reads are excluded and OperatorX invalidation purges its deployment subtree. See [OperatorX](./operatorx.md#compact-comparison-reads).
- `tco-feed` performs server-side frontier interpolation for spreadsheet consumers that cannot run the TypeScript transforms. Its assumptions (tier weights, workload mix, α) enter only as explicit query params with documented defaults, so a published sheet's URL fully records its methodology.
- `pareto` returns frontier and hinterland coordinates over stored benchmark rows with explicit axis preferences. It reuses the chart dominance algorithm without UI filters. See the [Pareto frontier and hinterland reference](../packages/skills/skills/inferencex-api/references/pareto.md).
- `gpu-metrics-point` is a point-detail BFF. It computes per-GPU statistics from stored samples on a cache miss and caches the payload by telemetry revision.
- `server-log-search` searches immutable log bundles in bounded database slices and returns only contextual matches. Returning raw rows would require transferring complete files that can exceed 100 MB before the browser could search them. A slice at character offset N makes PostgreSQL decompress the first N characters of the pglz-compressed value, so one search scans at most 64 million characters and returns `504` after 25 s. `server-log` never reads a file of unknown size whole: complete reads stop at 16 MiB and downloads at 512 MiB (`413`), and downloads stream 8 Mi-character slices. Neon's HTTP driver rejects responses over 64 MB. Ingest never rewrites stored log text, so `server-log` responses carry the `db-log` CDN tag with a one-year `s-maxage`, and only an immediate purge drops that tag.
- `/api/v1/overview` is a page-owned backend-for-frontend (BFF). It returns the compact `OverviewPageData` shape used by the initial server render, allowing selector changes to update the matrix without downloading every model's raw benchmark history or triggering a React Server Component (RSC) round trip. It is not a reusable public data API.
- `/api/v1/benchmarks?view=calculator&sequence=...` is a page-owned compact view. It returns only the selected calculator scenario and the metric keys needed for interpolation, while the default endpoint preserves the raw-row contract. This reduces transfer and browser parsing without narrowing the reusable inference response.

Two rules keep the overview BFF honest, both enforced in `overview-navigation.tsx`:

- **One cache key per data state.** Requests and the in-memory cache are keyed on a canonical href rebuilt from the resolved params (`overviewDataKey`), not the address bar. Explicit defaults, reordered params and campaign tags collapse to one key, so the CDN's day-long `s-maxage` is not fragmented by link variants.
- **`ref` never reaches that key.** The reference hardware only chooses which column the percentages are measured against, and every cost that needs is already in the payload, so the client derives it from the URL and recomputes the ratio per row. The server still resolves `ref` for SSR, shared links and no-JS.

On the server, `getOverviewPageData` caches one `OverviewCube` per (engine, compare, model scope), which comes to 20 entries. A cube holds each matrix cell's selected read and missing reason at all six tiers, with every selected serving series stored once, plus the baseline matrix in history modes. Tier, `ref`, `rows` and `hwrows` only slice it (`sliceOverviewCube`), so a new selector combination costs about a millisecond instead of reloading every model's rows and rebuilding the frontier. Keep anything that varies with those four selectors out of the cube. The cube is read with `shareDecodedResult`, so a warm request skips the brotli decode and JSON parse and pays only for the slice. Slicing must never mutate the cube, and nothing downstream may mutate the page data, because both share objects with the cube other requests read.

Because the selector commit uses `History.prototype.pushState` rather than Next's patched version, `useSearchParams()` and `usePathname()` stay at the load-time URL on `/overview`. Anything that needs the live URL there listens for `CLIENT_SEARCH_CHANGE_EVENT`. The provider calls `trackVirtualPageview`, which records a `$pageview` only when the pathname changes, so control changes are not pageviews. Do not add a `useSearchParams()` consumer to the overview tree.

## URL State Persistence

Chart filter state (model, sequence, metric, precisions, date range, GPU selections) is serialized to URL query params. This enables shareable links that reproduce exact chart views.

The two profit estimators use model slugs followed by named route pairs instead,
including on `/zh`: `/profit-estimator/deepseek-v4/target/24`.
Their existing query-key state store is adapted at the routing boundary by
`profit-estimator-routes.ts`. Shallow history replacements keep the address bar
current; these client-owned writes bypass Next navigation rehydration so it
cannot overwrite a pending control edit. Legacy query links remain readable.
Profit dashboards use P90 only and strip legacy percentile parameters.
Language links retain route state without copying it into the query string;
the unofficial-run filter reader and cross-tab overlay links use a separate
route-aware adapter. Tab links encode run IDs in the destination's format:
route segments for profit estimators, query parameters for other dashboards.
Other dashboards keep their existing query-state behavior.

**Why debounced writes (150ms)?** Rapid filter changes (e.g., clicking multiple precision checkboxes) are batched into one flush of the in-memory share state and, on profit-estimator routes, one shallow `replaceState` of the pathname instead of one history write per click.

**Why snapshot on load, without clearing the address bar?** Initial params are read once into the URL-state snapshot, and route-owned entry points can also pass typed server seeds. Subsequent debounced writes update the in-memory share state, not the address bar. The loaded params stay visible, so reloading a share link reopens the same view. An earlier load-time cleanup raced Next's hydration history write, which restored the params on some loads and not others.

**Prefix convention**: `g_` (global), `i_` (inference), `e_` (evaluation), `r_` (reliability), and `c_` (calculator). The canonical dashboard route registry declares which scopes belong in each share URL.

Inference places Scenario in the chart footer beside Cost Tier and TCO Basis on
desktop and mobile, including below an empty chart so users can recover from an
empty selection. PowerX keeps Scenario beside Model on
desktop and inside More chart controls on mobile. Both surfaces put Precision and
Run context inside More chart controls below `md`; Model stays visible. Desktop
keeps Precision beside Model and Run context full-width below chart settings.
Embedded charts retain their standalone run panel. This is a presentation-only API
coverage exclusion: expanding the section does not change scenario, precision, or
date/run selection, API parameters, defaults, measurements, or unofficial overlays.

## Analytics

PostHog loads after `window.load` plus an idle callback to keep it off the critical path. If the page is hidden (`visibilitychange` to hidden or `pagehide`) while events are still queued, it starts loading immediately instead, so a visitor who switches tabs or leaves before the idle callback still sends the pageview. It posts through the first-party `/ingest` rewrites in `next.config.ts`, with dead-click capture off and autocapture on. Network timing in recordings drops `search`, `q` and `query` URL params (`lib/analytics/network-request-mask.ts`) so typed search text is never captured.

Until the client loads, `track()` in `lib/analytics/analytics.ts` queues events (capped at `MAX_PENDING_EVENTS`, later events are dropped). Each queued event keeps the URL and time at which it was tracked and is replayed with PostHog's `timestamp` option. The first tracked event of a page load records that page's `$pageview` ahead of it, so page effects such as `landing_page_viewed` never precede the pageview.

Pageviews are manual. `PageViewTracker` records one per Next pathname or search change, deduplicated by URL. Model switches rewrite the pathname outside the Next router, so it also records a virtual `$pageview` (`navigation_type: 'client_pathname_change'`) on `CLIENT_PATHNAME_CHANGE_EVENT`, but only when the event detail has `pageview: true` (pass `{ pageview: true }` to `replaceClientPathname`/`replaceRouterPathname`). `GlobalFilterProvider` passes it only when the rewrite applies a model the user picked through `setSelectedModel`. Programmatic picks (URL presets, the profit estimator's model correction) call `setSelectedModel(model, { userSelection: false })`. Bare-route canonicalization (`/calculator` → `/calculator/<slug>`), filter-driven path rewrites (profit estimator) and query-only rewrites (filters, `/overview` controls) are not pageviews.

`inference_chart_rendered` fires once per navigation when the first chart has data points. `ms_since_navigation` counts from the latest navigation start (`lib/analytics/navigation-timing.ts`: document load, or the pathname change for soft navigations) and `soft_navigation` tells the two apart. Every pageview carries and registers `route_template` (for example `/inference/[model]`, shared by `/zh`) and `locale`, so pageviews and web vitals group by template. Add new dynamic routes to `lib/analytics/route-template.ts`.

A delegated click listener sends `outbound_link_clicked` (`host`, `path`, `is_newsletter`, `is_semianalysis`, `placement`) for links to other hosts. `placement` comes from the nearest `data-analytics-placement` ancestor. Use `analyticsPlacement()` from `lib/analytics/placement.ts` to set it. The header, mobile menu, footer, landing hero and sections, blog article body, glossary, compare and chips pages carry one. In-app CTA events read the same attribute through `placementFor(event.currentTarget)`. 404 pages send `not_found_page_shown`. Search events send `query_length` and result counts, never the typed text.

Mount-time events use `trackOncePerPageview` (once per page view, so remounts and StrictMode don't double count) or `trackOncePerSession` (sessionStorage). A failed React Query request sends `data_query_failed` (`endpoint`, `status`, `query_key`, `route_template`) once per query key per page view. Queries that throw to an error boundary are reported by `error_page_shown` instead.

Use the shared hooks instead of hand-rolled effects. `useSearchTracking` sends `<section>_searched` with `query_length` after typing pauses. `useDialogCloseTracking` sends `<section>_closed` with `duration_ms` whenever a tracked dialog, drawer or popover closes. Chart export, CSV, MP4 and zoom-reset events from `ChartButtons` send `chart` plus the dashboard selection. Pass `analyticsContext={selectionAnalyticsContext(...)}` (`model`, `sequence`, `precision`, `gpu_count`). `inference_*_selected` events spread `useInferenceAnalyticsContext()`.

Property keys are snake_case with one name per concept. Use `gpu` (or `gpus` for a list), `gpu_count`, `metric`, `sort_key` + `sort_dir`, `file_name`, `query_length`, and `enabled` for boolean toggle state. `lib/analytics/event-property-keys.test.ts` rejects camelCase and legacy keys (`hw`, `hwKey`, `expanded`, …) in tracking calls. Server events (`trackServer`/`captureServer`) always send `$process_person_profile: false` and should pass `route_template` when the route is known.

## Server-Side Caching

`cachedDerivedData()` is the tagged, `unstable_cache`-only wrapper for compact server payloads. Compare caches one pair-filtered, full-shape hydration row set per model/GPU pair, then recomputes the inexpensive sequence/precision table transform per request; nesting a selector cache around the pair cache would bypass Next.js incremental caching.

Next.js refuses to store a data cache entry whose serialized form passes 2 MB and only logs "items over 2MB can not be cached", so such a query reached the database on every read. `cachedQuery` therefore stores any result whose JSON passes 64 KiB as base64 brotli (quality 4) and decodes it on read. A cached read still returns the same JSON round trip as before. On production data `/api/v1/evaluations` (3.2 MB entry) and the `/api/v1/submissions` summary (3.9 MB) now stay cached at 166 KB and 116 KB.

Decoding still costs a brotli pass and a parse on every hit, which can be most of a request. `cachedDerivedData(fn, prefix, { shareDecodedResult: true })` keeps the last decoded value per argument list and returns that same object while the cached brotli string is unchanged. Hits on smaller, uncompressed entries still get their own parse. Use the option only when no caller mutates the result.

### ISR pages and initial data

Compare (`/compare`, `/compare-per-dollar`, `/compare-precision`, `/compare-spec-decode`, their `[scenario]` children and `/zh` mirrors), `/run` and `/rankings` detail pages return `[]` from `generateStaticParams()`. Nothing is prerendered at build time. Each URL renders on its first request and is then served from the ISR cache until an ingest marks the `db-page` tag stale. Every data read on these pages goes through `cachedQuery`, which tags the page, so `revalidate = 86400` is only a backstop for a failed purge. The exceptions are the `/compare-precision/[slug]` and `/compare-spec-decode/[slug]` detail pages (and their `[scenario]` children). Their benchmark reads are tagged only through the Blob purge-generation entry, which does not exist when Blob storage is disabled, so they keep `revalidate = 3600`. The index pages, `/overview` and `/inference/agentic` use the same daily backstop. The compare `opengraph-image` routes also return `[]`. Their PNG depends only on the slug, so each one renders on its first request and stays cached until the next deploy. Prerendering them cost about 2,000 PNG renders per production build.

`generateMetadata` and the page body read the same data in one render. `getComparePageDerivedData`, `getRunPageData`, `getRankingPageData` and `lookupDatasetPage` are wrapped in React `cache()`, so the second read reuses the first. Route handlers get no React cache, so the sitemap reads availability once and passes the rows to the slug-list helpers.

The calculator-family tabs (`/calculator`, `/fleet`, `/first-token`, `/cache-reuse`, `/profit-estimator`, `/profit-estimator-per-gigawatt`, their model and filter routes, and `/zh` mirrors) are static and never read `searchParams` on the server. The prerendered HTML is the route's no-query state. `CalculatorUrlSeedBoundary` reads the URL with `useSearchParams()`, which keeps the tool out of the prerender, so the client renders it from the URL (query plus profit-route path filters, `calculatorUrlSeed()`) instead of hydrating the default HTML. A deep link therefore shows the defaults only until hydration, and it never mounts or fetches with them. Because a static page cannot see the query, `src/proxy.ts` issues the query-preserving 308s that the pages used to, through `modelRouteRedirectUrl()`. That covers alias and mixed-case model slugs on every model-route tab (`/historical` included) and retired profit percentiles (`i_pctl`, `percentile`, or a `percentile` path filter).

Compare pages embed only the rows for the page's default sequence (`initialCompareBenchmarkRows()`), not the whole pair history. `InferenceContext` passes those rows through `resolveBenchmarkSeed()` (`components/inference/utils/benchmark-seed.ts`), which uses them only while the selection matches the seeded model and sequence, under a sequence-scoped query key. Picking another sequence falls through to the shared full-model benchmarks query, so a partial seed never answers for data it lacks.

The compare pages server-render the header, narrative and table. The chart below them (`InferenceDashboard`, which is `InferenceProvider` + `ChartDisplay`) mounts through `LazyCompareInferenceChart` (`next/dynamic`, `ssr: false`, a 600 px skeleton meanwhile), so its provider, benchmark fetch and D3 stack load after hydration instead of with the page's first-load JS. Likewise `UnofficialRunProvider` imports the benchmark transform (`providers/unofficial-chart-data.ts`, which pulls in the power model) only when the URL names unofficial runs, and withholds the run data until both the response and that module have arrived.

The dashboard shell and each heavy page tool are hydration islands. `hydrationIsland()` (`components/ui/hydration-island.tsx`) wraps a `next/dynamic` component (server-rendered, so its HTML is unchanged) in `<Activity mode="visible">`. Next.js renders `<link rel="preload" as="script">` tags for the island's chunks, so they download in parallel with the route's entry JS. They are not part of it, though, and React hydrates the rest of the page without waiting for them. React hydrates each Activity boundary on its own once its chunk has arrived, at low priority unless the user interacts with it first. Unlike a Suspense boundary, Activity is never streamed out of order, so the prerendered HTML stays in document order with no reveal script. On a client navigation the island chunk loads when the new page renders. The islands are `LazyDashboardShell` (the `(dashboard)` layouts), `LazyInferencePageIntro`, `LazyInferenceDashboard`, `LazyPowerXDashboard`, `LazyHistoricalTrendsDashboard`, `LazyEvaluationDashboard`, `LazyReliabilityDashboard`, `LazyFeedbackViewer`, the calculator-family displays (`lazy-calculator-displays.tsx`), the compare page clients (`lazy-page-client.tsx`), `LazyUnofficialRunProvider` (model, compare and embed layouts), `LazyEmbeddedModelDashboard`, `LazyOverviewPageContent` and `LazyNudgeEngine` (overview layouts). A page keeps only its server-rendered intro and these small wrappers in its first-load JS.

The overview page (`/overview`, `/zh/overview`) is prerendered with the default controls and ignores `searchParams` on the server. When a shared URL asks for other controls, `OverviewNavigationProvider` loads that state from `/api/v1/overview` after mount.

### API responses

`cachedJson()` (`lib/cache/api-cache.ts`) takes the incoming request. It serves brotli, then gzip, then plain JSON according to `Accept-Encoding`, so a client that sends no header (curl, scripts) gets plain JSON. Every response carries `Vary: Accept-Encoding` and a strong `ETag` hashed from the payload and the chosen encoding. A matching `If-None-Match` returns a bodiless `304`. Brotli runs at quality 9 below 1 MiB of JSON, 8 up to 4 MiB and 7 above. On the production payloads that keeps every body within 2.3% of quality 9 and cuts the brotli CPU by about a third (the 12.7 MB history payload goes from 396 ms to 228 ms). A lower quality is part of the ETag (`"<hash>-br8"`, `"<hash>-br7"`), because the encoded bytes differ. Responses with a `version` ETag are validated before the body exists, so they always use quality 9. Route handlers that call other handlers directly use `sourceRequest()`, which sends no `Accept-Encoding`, so they always read plain JSON. Benchmark rows skip that hop. The views and `/api/v1/pareto` call `loadBenchmarks()` (`lib/benchmarks/benchmarks-endpoint.server.ts`), which returns the rows `/api/v1/benchmarks` serializes without stringifying, hashing and re-parsing them.

The Vercel CDN keys `Vary: Accept-Encoding` on the raw header string, so `gzip, deflate` and `deflate, gzip` are separate entries and separate origin misses. `/api/v1/benchmarks`, the busiest programmatic route, passes `compression: 'cdn'`: it sends plain JSON without `Vary`, the CDN keeps one entry per URL, and the CDN compresses that entry for each client. The route also validates every query parameter before reading the database (`lib/benchmarks/benchmark-request-params.ts`), so malformed values return 400 instead of a Postgres cast error.

`Cache-Control` is `public, max-age=60, s-maxage=86400, stale-while-revalidate=86400`. Vercel strips `s-maxage` and `stale-while-revalidate` before the browser, so a browser reuses a response for 60 s and then revalidates it with its ETag, which costs a round trip but no body. Browsers get no stale-while-revalidate window, which keeps a returning visitor from seeing pre-ingest data for longer than a minute.

Fixture builds (`E2E_FIXTURES=1`) send `Cache-Control: no-store` instead, so every E2E request reaches the network where `cy.intercept` stubs it.

The `/reliability` and `/evaluation` dashboards read page-owned compact forms of the published lists. `/api/v1/reliability/daily` sums the `run_stats` rows per day and GPU (about 7x fewer rows), which leaves every date-range rate unchanged. `/api/v1/evaluations/compact` sends each config's columns and each run's timestamp and URL once, plus only the five metric keys the chart reads (`compact-rows.ts`). The published routes are unchanged.

The dashboard filters read `/api/v1/availability/compact` instead of the published `/api/v1/availability`. A published row is a line (model, ISL/OSL, precision, hardware, framework, spec method, disagg, benchmark type) on one date, and a line repeats on many dates. The route sends each line once, with its strings as dictionary indexes and its dates as `[gap, length, ...]` runs over the sorted dates (`compact-availability.ts`). It adds the supplemental datasets the browser used to append, and a cold fill reads the published route's cache slot. On production data that is 780 lines for 7,072 rows, 42 KB of JSON instead of 1.32 MB, and 5.9 KB of brotli instead of 22.5 KB. The browser decodes it once into an `AvailabilityIndex` (`availability-index.ts`) in about 0.3 ms, where parsing the rows took 2.0 ms. Every line keeps its derived sequence and chart hardware key and a date bitset, and lines are grouped by model. `GlobalFilterProvider`, `InferenceProvider` and the profit history filters walk the selected model's lines and OR their bitsets, so they no longer rescan every row with `rowToSequence` and `buildAvailabilityHwKey` on each memo. A model, sequence or precision change recomputes those filters 13-18x faster. Lines keep the order of their first row, which keeps first-seen orders (the sequence list, precision curve counts) the same as the rows give. `availability-index.test.ts` checks every derived value against the row scans for every model, sequence, precision and GPU selection. The published route is unchanged.

The inference charts decide whether a point offers "View charts" and "View logs" from `/api/v1/benchmark-presence`. It takes no parameters, so every chart view shares one CDN entry per ingest. The body lists the ids with a stored trace and the ids with a linked server log as `[gap, length, ...]` runs of consecutive ids, because ingest numbers a run's rows adjacently. On production data that is 1.1k runs for 26k ids, 6.1 KB of JSON and 1.9 KB brotli. The browser decodes each list once into a bitset (`IdBitset`, about 0.06 ms) and tests one bit per point. The published `?ids=` routes `/api/v1/trace-availability` and `/api/v1/log-availability` answer from the same cached runs (`presentIds`), so they no longer query the database per id set, and their responses are unchanged.

Historical Trends reads `/api/v1/benchmarks/history/trends` instead of the published history. The route compacts the same cached rows (`trend-history-rows.ts`). Each config's columns and each run's provenance are sent once, and a row keeps only the metric keys some trend metric reads, as index and value pairs. Fixed-sequence rows carry their median interactivity, and agentic rows carry the P90 ITL inputs. `power_audit` keeps only the CPU audit that the modeled rack power checks, and `power_invalid_reasons` is dropped. For the largest history (gpt-oss-120b 1k/1k, 10,045 rows) the body falls from 12.0 MB to 0.98 MB of JSON and from 1.50 MB to 0.41 MB of brotli. Every trend metric draws the same lines from either form, and `trend-history-rows.test.ts` checks that against the fixture history.

`/api/v1/gpu-metrics-point` cannot be cached by the CDN, because a re-ingest changes the telemetry behind an unchanged URL. It sends `Cache-Control: private, no-cache` with an ETag derived from the payload cache prefix, the point id, the live telemetry revision and the encoding (`cachedJson(..., { version })`). Each request reads the revision first, and `notModifiedJson()` answers a matching `If-None-Match` with a `304` before the payload is loaded, serialized or compressed. Missing points and errors stay `no-store`.

Server data (`unstable_cache` plus Blob) and CDN responses (the `db-cdn` tag) are tagged separately. `cachedQuery` keeps two `unstable_cache` entries per query. Route handlers read the `db`-tagged one, and ISR renders (sitemap included) read a separately keyed `db-page` one. On ingest, `purgeAll()` deletes the blobs, expires `db` immediately, and only marks `db-page` and `db-cdn` stale (`revalidateTag(tag, 'max')`). The next visitor gets the previous response at once while the CDN refetches in the background, and that refetch reads the database because the route entries are already gone. Expiring route data with `'max'` instead would hand the stale entry to the CDN's refetch and cache it for another day. ISR pages keep serving their previous HTML, because a stale `unstable_cache` entry is refetched in the foreground during regeneration, and the stale value is kept if that refetch fails. Corrections and retractions (`apply-run-overrides.yml`, `cache-refresh.yml`) run `admin:cache:invalidate <origin> --immediate`, which posts `/api/v1/invalidate?immediate=true` and expires every tag outright so retracted data is never served again. CollectiveX and OperatorX have no server data layer, so their tags are marked stale too, and their scoped purges (`?scope=collectivex` or `?scope=operatorx`) also honor `immediate=true`. Deleting a CollectiveX run purges immediately, because the admin who deleted it reloads right away.

The ingest workflow then runs `bun run admin:cache:warmup <origin> --dashboard`, and production promotions run the same warmup in `warm-after-deploy.yml`. The script requests the dashboard APIs with a browser `Accept-Encoding` and reads every body, because the CDN keeps one variant per encoding and only caches a streamed response that was read to the end. The post-ingest PowerX verifier sends `Pragma: no-cache`, which makes the CDN revalidate a stale entry before it answers.

Vercel Blob counts every deleted blob as one operation toward its rate limit (4,500 a minute on Pro), and a purge can delete a few thousand blobs while live traffic shares the same budget. `blobPurge()` therefore deletes in batches of 100. When Blob answers `rate_limited`, it waits the returned `retryAfter` (60 s) and resends that call, up to three waits per purge so the request stays inside the 300 s function limit. The blobs are deleted before any tag expires, so a purge that still fails leaves every tag untouched and the next invalidation redoes it.

Blob entries (`cachedQuery(..., { blobOnly: true })`, `lib/cache/blob-cache.ts`) hold the JSON brotli-compressed at quality 4 under `<prefix>/generation/<id>/<key>.json.br`, 6-9x smaller than the JSON on benchmark payloads. A read is one `get()` request, because the SDK builds the store URL from the token. A `get()` goes through the Blob CDN, which can keep serving a deleted object for a short while, so a path is never reused after a purge. The generation id is itself a `db`-tagged `cachedQuery` entry (`db-page` during ISR), and `purgeAll()` expiring that tag moves every later read to new paths. OperatorX comparisons are keyed by their source revisions (`revisioned: true`), so they stay outside the generation and keep their own purge. Concurrent calls for one key in an instance share a single read, query and write, and each caller parses its own copy of the JSON. The SSR helpers in `benchmark-data.server.ts` and the routes read latest benchmarks through one canonical key, so a page render and `/api/v1/benchmarks` share an entry, and calculator views trim the same cached rows instead of querying again.

`/api/v1/benchmarks` also keeps its final response in Blob (`cachedJsonResponse`, `<key>.response.br` in the same generation): the brotli body behind one quality byte and the 32-character ETag digest. A CDN miss after the first fill reads that object and serves it with the headers and ETag `cachedJson` would send for the same options. The route passes `compression: 'cdn'`, so every miss decodes the stored body to plain JSON for the CDN to compress. For DeepSeek-R1 (2.3 MB of JSON) that skips about 51 ms of CPU per miss, which went to decoding and parsing the stored rows, stripping fixed-sequence run metadata, serializing and hashing. The first request per generation pays it once, and the post-ingest warmup makes that request.

## React Query Configuration

- **staleTime Infinity / gcTime Infinity**: Data changes only when CI ingests new results. Infinite TTLs mean React Query never refetches or garbage-collects on its own — data is fetched once per page load and held for the session. The server-side CDN cache ensures fast responses. Keys use canonical values (sorted, deduplicated ids, `''` for the latest date), so equivalent requests share one cache entry.
- **No waterfall to the first chart**: the latest benchmarks request depends only on the model, so the inference chart starts it in parallel with `/api/v1/availability/compact` through a second observer on the same query key (`prefetchLatestRows` in `useChartData`). A disabled observer still returns cached data, so while the prefetch runs `useChartData` ignores the rows it reads from that key and keeps the chart loading. Once the sequence resolves, the gated query reads the cached entry without another request, and the chart never renders the default sequence first. `workflow-info` still waits for the resolved run date.
- **Bulk id lookups** (`useBulkIdsQuery`): requests are split at each route's id limit, and ids that a fresh lookup for the same endpoint already covered are not requested again. A chart whose visible points change as filters settle therefore fetches only the new ids. Freshness is tracked per id from its original fetch, so reused ids never outlive the 5-minute stale time.
- **Revalidated by-id payloads** (`useByIdQuery(..., revalidate)`, used by `useGpuMetricsPoint`): the query refetches on every mount and window focus and sends the cached payload's ETag. An unchanged revision returns a bodiless `304` and the cached object is reused as is, so nothing is parsed or re-rendered. A re-ingested point returns the new payload on the next open or focus.
- **refetchOnWindowFocus: false**: Users tab away to reference articles, then come back. Auto-refetching would cause jarring chart rebuilds and lose zoom state.
- **Placeholder data** (opt-in per hook, e.g. `useBenchmarks` with `keepPreviousForModel`): when the date or run changes within one model, the old chart stays visible during the fetch. Another model's rows are never used as a placeholder, and neither are rows from a differently scoped key (a one-sequence compare seed), which would render an empty chart. Without this, users see a loading skeleton for 200-500ms on every such change.
- **retry: 1**: Single retry catches transient network blips. More retries would delay error display for actual outages.

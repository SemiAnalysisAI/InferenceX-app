## Blackwell 特性

从 Hopper 到 Blackwell，NVIDIA 对架构进行了若干渐进改进，并改变了 MMA 相关指令的 PTX 抽象。我们在 [NVIDIA Tensor Core 演进](https://newsletter.semianalysis.com/i/174558646/blackwell)一文中讨论过其中大部分内容，主要变化包括：

- 引入 tensor memory（TMEM）存放 MMA 累加器。线程不再隐式拥有 MMA 结果，而由软件在 MMA 作用域内显式管理 TMEM。
- `tcgen05` 操作改由单个线程代表整个 CTA 发起，不再像之前几代那样以 warp 或 warpgroup 为作用域。CuTe MMA atom 也体现了这一变化：[Blackwell](https://github.com/NVIDIA/cutlass/blob/main/include/cute/atom/mma_traits_sm100.hpp#L1045) 使用 `ThrID = Layout<_1>`，而 [Hopper 的 warpgroup 级 MMA](https://github.com/NVIDIA/cutlass/blob/main/include/cute/atom/mma_traits_sm90_gmma.hpp#L491) 使用 `ThrID = Layout<_128>`。
- 支持 TPC 作用域的 TMA 和 MMA，由一对协调执行的 CTA 共同工作，在 PTX 中表现为 `cta_group::2`，在 SASS 中表现为 `2CTA`。组成一个 TPC 的两个 SM 可以对共享操作数执行 `tcgen05.mma`，降低每个 CTA 对 SMEM 带宽的需求，支持更高运算强度的 MMA 指令。后文会说明，要充分使用可用 MMA 吞吐，这种操作数共享是必要的。
- 原生支持带 micro-scaling 的亚字节数据类型。
- [Cluster Launch Control（CLC）](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/blackwell_cluster_launch_control.html) 为 persistent-CTA kernel 中的动态工作调度提供硬件支持，后续文章会讨论。
- Hopper 引入的 [Programmatic dependent launch（PDL）](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html) 用于隐藏连续 kernel 的 launch 和准备延迟，后续文章会讨论。

## Cluster、GPC 与 floorsweeping

从 Hopper 开始，Nvidia 数据中心 GPU 支持一项可选功能，常见名称包括 thread block cluster、CTA cluster 和 cooperative grid array（CGA），指的都是同一功能。Cluster 是 CTA 的逻辑分组，其形状和大小可以针对每个 kernel 静态或动态指定。编程模型可以利用这一层分组，例如向同一 cluster 中的多个 CTA 执行 multicast load；后面讨论 TMA multicast 时会进一步说明。

重要的是，同一 cluster 内的 CTA 保证在同一个 GPC 上共同调度。这对每个 SM 只有一个 CTA 的 persistent-CTA Blackwell kernel 有直接影响：如果 cluster 大小不能整除 GPC 中的 SM 数，一部分 SM 就会闲置。不了解文档中很少介绍的 GPC 的开发者，可能在启用 cluster 后仍按 SM 总数 launch 同样多的 persistent CTA，结果部分 CTA 被迫串行执行。

每个 GPC 中可用的 SM 数并不固定，同一芯片内不同 GPC 之间可能不同，同一封装的两个裸片之间也未必对称。半导体制造中的缺陷可能出现在芯片各处，因此 Nvidia 必须设计一种机制，将通过测试的单元以相对统一的方式暴露给软件。

我们让 Claude 编写了一个工具，通过 launch 不同大小的 cluster，并用 PTX `%%smid` 记录哪些 SM 出现在同一 GPC 中，反推 SM 与 GPC 的映射。得到的是 TPC 到 GPC 的逻辑分组列表。列表长度超过 Hopper/Blackwell 实际拥有的 8 个 GPC，因为部分 TPC 看起来独占一个逻辑 GPC，从未与其他 TPC 共同调度。

  alt="从 cluster 调度推断的逻辑 GPC 与 TPC 分组"
  caption="[来源： SemiAnalysis](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor)"
/>

从 SM100 开始，NVIDIA 为这种分配粒度问题提供了解法：kernel 可以同时指定首选 cluster 大小和回退 cluster 大小，既获得较大 cluster 的好处，又利用所有可用 SM。通常，要用满 GPU，回退 cluster 大小应设为 2 或 1。

### 逻辑 GPC 与物理 GPC

前面展示的 TPC 到 GPC 分组是逻辑分组，表示软件看到的 GPC，并不说明每个 GPC 的 20 个物理 SM 中哪些被启用，也不说明各物理 GPC 在两个裸片上的位置。实际中，逻辑配置相同的 B200，各 GPC 中通过测试的物理 SM 也未必相同。对软件而言看似一样的 GPU，性能可能因此有所差异。此外，逻辑 SM/GPC 分组无法告诉我们某个 GPC 位于 B200 封装内的哪个裸片。

为了进一步了解 SM 的物理布局，我们让每个 SM 遍历一个填满 L2 cache 的指针链，并测量每次 load 的延迟。针对每个地址，将一个 SM 的延迟与所有其他 SM 比较，形成 SM&lt;->SM 距离矩阵，横纵坐标均为 SM ID。

## 内存子系统

本节讨论内存子系统，也就是在计算单元之间搬运数据的硬件。内存 copy 指令利用这些单元工作，较新架构还支持异步 copy，异步机制的演进可见[上一篇文章](https://newsletter.semianalysis.com/i/174558646/asynchronous-execution)。这里重点研究两种异步 copy 指令：LDGSTS 和 TMA（Tensor Memory Accelerator）。

### 异步 copy

Async copy 在 Ampere 引入，PTX 为 `cp.async`，SASS 为 `LDGSTS`，用于异步将数据从 global memory 搬到 shared memory。它不会阻塞，因此可让 memory load 与计算重叠。数据直接写入 shared memory，不经过寄存器，也降低了寄存器压力。

参考 FlashInfer 的多头注意力（MHA）kernel，我们测试了以下配置：

- 每个 SM 的 CTA 数：1、2、3、4
- Stage 数：1、2、4
- 每个 CTA 的线程数：64、128、256
- Load 大小：4B、8B、16B

我们以每个 SM 的 bytes in flight 为横坐标绘制吞吐。它表示并发 memory load 指令正在加载的总字节数。

虽然相同 bytes in flight 下，不同 load 大小的吞吐趋于接近，我们仍更倾向于 16-byte load。它在相近 bytes in flight 下吞吐略高，且占用的执行资源更少。例如，32 KiB in flight 时，8B load 需要 4 个 stage，16B load 只需 2 个，可以少用两个 memory barrier 对象的空间，也降低指令发射压力。

总体来看，`LDGSTS` 在 32 KiB in flight 左右达到约 6.6 TB/s 的带宽上限。

### Tensor Memory Accelerator（TMA）

TMA 在 Hopper 引入，PTX 为 `cp.async.bulk.tensor`，SASS 为 `UTMALDG`。它是一种异步数据 copy 引擎，专门处理从 global memory 到 shared memory 的大批量数据搬运。单个线程即可发起 TMA，由它完成地址生成、memory swizzling 和越界处理，其他线程则可执行独立工作。这里测试二维 tensor 版本 cp.async.bulk.tensor.2d，以代表典型 TMA 用法。

参考 FlashInfer 注意力 kernel，我们为每个 SM 分配一个 CTA，并在每个 CTA 的 1 至 4 个 warp 中各用一个线程发起不同 box 大小的 TMA 指令。下图展示各 bytes in flight 下的最佳吞吐。

TMA 测试配置如下：

- 每个 SM 的 CTA 数：1
- 每个 CTA 的线程数：128，即 4 个 warp
- TMA box 维度：从 32x8 到 128x128 的二维形状

### Async copy 与 TMA 对比

FlashInfer 等深度学习 kernel 库同时使用 TMA 和 async copy 加载数据。两者性能特征不同：TMA 适合访问规则的大批量 load，但延迟较高；async copy 可以处理不规则访问，却受到大小限制。我们希望说明各自在什么条件下更合适，因此测试了 FlashInfer 的 MHA 和 MLA kernel 所用配置。

从吞吐看，在少于 32 bytes in flight 时，async copy 略好于 TMA；超过之后 TMA 追上，并能继续扩展到 128 KiB。从延迟看，在 12 KiB in flight 之前，async copy 略低于 TMA，之后 TMA 延迟明显增加。

实际中，Blackwell MLA kernel 使用 async copy 动态加载 page，而 MHA kernel 只使用 TMA。FlashInfer 的大部分 Blackwell MHA kernel 来自 TRT-LLM，因此我们只能通过分析二进制推测实现。我们发现，与 Hopper 类似，所有 Blackwell TRT-LLM kernel 都使用 TMA。对于动态 page 加载，我们猜测它们沿用 Hopper 的做法，使用 4D TMA，将 page index 作为最后一维，并在需要时索引 `TensorMap` 对象。为了明确这些 kernel 的实现机制，我们呼吁 NVIDIA 开源 FlashInfer TRT-LLM kernel，让社区受益。

### TMA multicast

TMA 支持 multicast：一次 load 将数据复制到多个 SM 的 shared memory，通过 CTA mask 指定目标。GEMM 类计算经常使用它，让处理不同输出 tile 的 SM 共享输入 tile。例如，SwiGLU 激活函数采用两个 GEMM 共享同一个输入矩阵的模式，适合 multicast。主要收益是减少 HBM load，降低有效带宽需求；同时，多个 CTA 对共享数据的请求被合并为一次，也显著减少 L2 流量。

根据 NCU 文档，处理 TMA multicast 请求的单元称为 L2 Request Coalescer（LRC）：

> L2 Request Coalescer（LRC）处理发往 L2 的请求，并尝试在转发到 L2 cache 前合并读取请求。它还处理来自 SM 的程序显式 multicast 请求，并支持写入压缩。

这似乎意味着，即使程序未显式要求，硬件也可能提供某种 multicast 行为，类似 miss status holding register。为验证这一点，我们运行相同的 TMA multicast 测试，但不再由一个 CTA 发起 multicast load，而是让所有 CTA 分别向相同数据发起独立 TMA load。

我们比较三种情况：

- 每个 SM 加载不同数据，作为基线。
- 显式 TMA multicast：每个 cluster 中一个 CTA 向该 cluster 的所有 CTA 发起 multicast load。
- 隐式 TMA multicast：每个 cluster 的所有 CTA 各自向同一数据发起普通 TMA load。

即使数据尚未驻留 L2，TMA multicast 也能大幅提高填充 SMEM buffer 的 load 带宽。对于已知流量模式，显式 TMA multicast 指令完全消除了重复 L2 流量，达到理想的“每个 SMEM 字节对应 1 / cluster_size 个 L2 字节”。在这个简单测试中，显式和隐式方式几乎达到相同的 SMEM 填充吞吐。不过 LRC 并不完美：隐式方式给 L2 带来的流量略多，且总数据量越大，这一点越明显。

### DSMEM 与 SMEM

NVIDIA 在 Hopper 中引入 distributed shared memory（DSMEM），允许同一 cluster 内的 CTA 访问彼此的 shared memory，可用于跨 CTA reduction 等模式。通过 DSMEM 读取其他 CTA 的内存，吞吐明显低于本地 SMEM 的每时钟周期 128 bytes。

我们测试了几种访问 DSMEM 的 PTX 模式。一个重要区别是，DSMEM load 与 global load 类似，按 packet 传输。因此，最优访问方式不像本地 SMEM 为避免 bank conflict 而采用的交错访问，更像 GMEM 中对连续位置的合并访问。此外，要让本地 SMEM 达到完整的 128 B/cycle，必须使用不带 `::cluster` 的 `ld.shared`。我们一开始用 `ld.shared::cluster` 同时访问本地和远端 SMEM，因而踩到了这个坑：`ld.shared` 会生成 `LDS`，而 `ld.shared::cluster` 生成通用的 `LD`，后者似乎无法达到本地 SMEM 的峰值吞吐。使用 `ld.shared::cluster` 时，我们也难以进一步提高性能；直到改用 `cp.async.bulk`（PTX）/ `UBLKCP`（SASS），让每条指令搬运更多数据，才把 DSMEM 吞吐略微提高。

下图是各 PTX 模式达到的峰值吞吐，以每时钟周期字节数（B/clk）表示，便于与本地 SMEM 的已知最大吞吐比较。

## 第五代 Tensor Core MMA

MMA 是执行矩阵乘法的核心指令。从 Hopper 到 Blackwell，MMA 性能越来越依赖形状。我们遍历不同形状与数据类型，量化这些差异。

Blackwell 引入了 2SM MMA，即 `.cta_group::2`，由一对 CTA 在两个 SM 上合作完成一次 MMA。具体而言，输入矩阵 A 被复制，矩阵 B 和 D 则分布在两个 SM 上，两个 CTA 可以访问彼此的 shared memory。这支持更大的 MMA 形状。我们将检验 2SM MMA 是否具有弱扩展、强扩展，或同时具有两者。

### 吞吐

NVIDIA 对不同输入类型给出了吞吐指标。这里将各“数据格式 + CTA group”组合的宣称值与实际可达最大吞吐比较。结果表明，所有格式及 CTA group 的 UMMA 都能接近峰值，包括可能存在协调开销的 2SM 版本。

<Figure
  src="/images/dissecting-nvidia-blackwell-tensor/mma-peak-throughput.png"
  alt="实测 MMA 吞吐量相对于理论峰值的比例"
  caption="[来源： SemiAnalysis](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor)"

对于 1SM MMA，在所有 N 大小下，较小的 M=64 最多达到理论峰值的 50%，较大的 M=128 则接近 100%，证实 M=64 只使用了一半数据通路。对于 2SM MMA，M=128 在 N=64 时从峰值的 90% 起步，其他 N 大小接近 100%。M128N64 必然受到 TMEM、L2、SMEM 等其他硬件单元限制。M=256 则在所有配置中维持接近 100%，因为它相当于每个 SM 的 M=128，能够用满数据通路。相同位宽的数据格式吞吐一致，micro-scaling 类型几乎没有额外开销。

<Figure
  src="/images/dissecting-nvidia-blackwell-tensor/mma-shape-throughput.png"
  alt="不同形状和数据格式下的 MMA 吞吐量"
  caption="[来源： SemiAnalysis](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor)"
/>

MMA 支持两种 AB 布局：A、B 都在 SMEM 中的 SS，以及 A 在 TMEM、B 在 SMEM 中的 TS。M=128 时，TS 布局接近峰值，而 SS 在较小 N 下较慢，到 N=128 才追上。

<Figure
  src="/images/dissecting-nvidia-blackwell-tensor/mma-operand-layout-throughput.png"
  alt="shared memory 与 tensor memory 操作数布局下的 MMA 吞吐量"
  caption="[来源： SemiAnalysis](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor)"
/>

可以证明，这是因为 SS 模式下 N&lt;128 时，指令本身受 SMEM 带宽限制。以 FP16 为例，已知硬件每个 SM 每周期可执行 8192 MMA FLOPs，SMEM 带宽为每个 SM 128 B/cycle。对于 M=128、N=64、K=16：

`A_bytes = 2*M*K = 4096; B_bytes = 2*N*K = 2048;`

`FLOPs = 2*M*N*K = 262144`

`SMEM Cycles = (A_bytes + B_bytes) / (128 B/clk) = 48 cycles`

`Math Cycles = FLOPs / (16384 FLOPs/clk) = 32 cycles`

转载编者注：原文上段给出 8192 FLOPs/clk，但公式分母写成 16384，同时仍给出 32 cycles。262144 除以 16384 等于 16；使用 8192 才得到 32。这里保留原文数字，并明确指出不一致，不能将该公式视为经过验证的重新计算。

继续增大 N，可以发现从 N=128 开始，指令才受计算限制。

<Figure
  src="/images/dissecting-nvidia-blackwell-tensor/mma-memory-compute-cycles.png"
  alt="不同 MMA 指令形状的 shared memory 与计算周期下限"
  caption="[来源： SemiAnalysis](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor)"
/>

其他数据类型也类似：两项操作数都在 SMEM 中时，N&lt;128 的 MMA 指令受 SMEM 限制。

### 不同在途指令数下的吞吐
